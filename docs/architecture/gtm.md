# Google Tag Manager (GTM)

## What GTM is

[Google Tag Manager](https://tagmanager.google.com/) is a tag-management system - a "tag" being one vendor's tracking snippet, historically a <script> or 1×1 pixel pasted by hand into your HTML - that lets marketing configure and update third-party marketing/advertising tags (Google Ads, Facebook Pixel, LinkedIn Insight Tag, etc.) from the GTM web UI without needing a code deploy. The app's only responsibility is to load the GTM container and push semantic events onto the browser's `dataLayer`; GTM's own trigger/tag configuration (owned in the GTM UI, not in this repo) decides what happens with each event. The most common use case for GTM tags is to listen for one of the events emitted by the code and dispatch a corresponding event to another marketing platform (e.g., Google Analytics, LinkedIn, Facebook) with the payload expected by that platform.

GTM is a separate system from [PostHog](/README.md#configuring-posthog-support), which this app also uses for product analytics and feature flags. Both sit behind the same `analytics` facade (see [Pushing events](#pushing-events)), and a few facade methods send to both: `analytics.siteSearched` fires GTM `site-search` and PostHog `search_update`, and `analytics.checkoutCompleted` fires GTM `checkout-completed` and PostHog `checkout_completed`. They are independent tracking systems serving different consumers (marketing/ads vs. product analytics), not duplicates of each other.

## How it's used

### Loading the container

The GTM container is loaded in the root `(site)` layout: `frontends/main/src/app/(site)/layout.tsx`.

| Env var           | Purpose                                                                                                                    |
| ----------------- | -------------------------------------------------------------------------------------------------------------------------- |
| `GTM_TRACKING_ID` | GTM container ID (e.g. `GTM-NMJ2CT6T`)                                                                                     |
| `GTM_AUTH`        | GTM environment auth token (not a secret — scoped per GTM environment)                                                     |
| `GTM_PREVIEW`     | GTM environment/preview identifier (e.g. `env-3`). Matches the snippet provided by Google Tag Manager install instructions |
| `GTM_COOKIES_WIN` | Optional, defaults to `"x"` if unset. Matches the snippet provided by Google Tag Manager install instructions              |

If `GTM_TRACKING_ID`, `GTM_AUTH`, or `GTM_PREVIEW` is missing, GTM is skipped entirely. Local values live in `env/frontend.local.env`; see `env/frontend.local.example.env` and `env/shared.local.example.env` for the template (dev values are copied from the GTM Environments UI).

### Pushing events

Analytics code lives in `frontends/main/src/common/analytics/`, in two layers:

- **`index.ts` — the `analytics` facade.** This is the only thing application code imports (`import { analytics } from "@/common/analytics"`). Each method is named for the user action (`analytics.courseEnrolled`, `analytics.siteSearched`, …) and routes it to GTM, PostHog, or both. ESLint (`import/no-restricted-paths` in `frontends/.eslintrc.js`) stops anything under `app/`, `app-pages/` or `page-components/` from importing `gtm.ts` or `posthog.ts` directly.
- **`gtm.ts` — the GTM adapter.** At the top of the module is a single low-level primitive:

  ```ts
  const pushGtmEvent = (event: string, payload: DataLayerPayload = {}) => {
    if (typeof window === "undefined") return
    try {
      window.dataLayer = window.dataLayer || []
      window.dataLayer.push({ ...payload, event })
    } catch {
      // Prevent analytics failures from impacting the app flow.
    }
  }
  ```

  Every GTM event is a small `track*` wrapper around `pushGtmEvent` that names the event and shapes its payload (e.g. `trackCourseEnrolled`, `trackSiteSearch`). Only the facade calls these wrappers, and nothing outside `gtm.ts` calls `pushGtmEvent` or touches `window.dataLayer` (apart from the GTM loader snippet in the layout). This keeps event names and payload keys centralized in one place rather than scattered as string literals across the app.

### UTM helpers

`frontends/main/src/common/analytics/utm.ts` parses `utm_source`, `utm_medium`, `utm_campaign`, `utm_term`, `utm_content`, `gclid` and `li_fat_id` from the URL query string and classifies the traffic (all string comparisons are case-insensitive):

- **Google ad**: `gclid` is present, or `utm_source=google` with `utm_medium` one of `cpc`, `ppc`, `paidsearch`, `paid`.
- **LinkedIn ad**: `li_fat_id` is present, or `utm_source=linkedin` with `utm_medium` one of `cpc`, `paid`, `paid-social`, `paidsocial`.
- **Organic social**: `utm_medium` is one of `social`, `social-organic`, `organic-social`, `organicsocial` (any source).

`analytics.adArrived` (`trackAdArrival` in `gtm.ts`) fires at most one ad-arrival event.

## Adding a new event

1. Add a `track*` wrapper to `frontends/main/src/common/analytics/gtm.ts` that calls `pushGtmEvent` with a new, stable event name and an explicit payload shape (define a `type` for the payload if it has more than one field).
2. Expose it as a method on the `analytics` facade in `frontends/main/src/common/analytics/index.ts`. Name the method after the user action, and re-export any payload type from `index.ts`. If the action should also go to PostHog, call `capturePostHog` from the same method.
3. Call `analytics.<method>()` from the component/hook where the user action or lifecycle moment actually occurs. Don't import `gtm.ts` or call `pushGtmEvent` from application code; ESLint will reject it.
4. Add the corresponding trigger/tag configuration in the GTM UI (outside this repo).
5. Update the tables above.
